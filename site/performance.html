Performance tuning

A measured 2.5× read reduction on the Developer estate

One predicate rewritten, measured with actual execution plans on 20,000 transfers. The scan and the seek return the same 6,695 rows; the difference is 156 logical reads against 63.

Case 1

The predicate, not the server

A transfer/account join filtered by year and month: YEAR(CompletedAt) = 2026 AND MONTH(CompletedAt) = 11 is not searchable, because the column is wrapped in a function. Rewriting it as a half-open range restores the seek.

-- scan: 156 logical reads, 20,000 rows read, 6,695 rows matched
WHERE YEAR(CompletedAt) = 2026 AND MONTH(CompletedAt) = 11

-- seek: 63 logical reads, 6,695 rows read, 6,695 rows matched
WHERE CompletedAt >= '2026-11-01' AND CompletedAt < '2026-12-01'

Source: actual execution plans captured on Adeola (Enterprise Developer 17.0.1000.7) on 2026-11-24, against AFS_CoreBanking.account.Transfer with 20,000 rows and a warm cache, via SET STATISTICS XML ON. Raw plans and counters: a timing run against the live instance on 2026-11-24 and dev_perf_q2_actual.txt. Logical reads repeated exactly across three runs; elapsed time moved between 5 and 32 ms, so reads are the figure quoted. Earlier measurements on LocalDB and on AccountLedgerEntry gave different absolute numbers, which is why the environment and table are named here.

Maintenance

Index and statistics health

Unused since restart

Four indexes had zero seeks, scans and lookups while still paying update cost: IX_account_Account_Status, UQ_account_Account_AccountNumber, IX_account_Transfer_CompletedAt, IX_account_Transfer_Currency_CompletedAt.

They are not dropped: a small test workload is not evidence that an index will stay unused once real reporting runs.

Missing-index suggestions

None returned by sys.dm_db_missing_index_details for the workload executed so far, so no index has been added on the strength of one small read. Candidates are revisited when the workload is large enough to rank them.

At volume

What an index actually did at one million rows

The 20,000-row estate cannot show an index's effect, so the same month filter was run against a throwaway table of 1,000,000 transfers spanning 37 months. Reads come from SET STATISTICS IO and the plan shape from SHOWPLAN_TEXT, both per statement.

ConfigurationPlanLogical readsElapsed
No index on CompletedAtClustered Index Scan6,700303 ms
Index on (CompletedAt)Clustered Index Scan — index ignored6,700410 ms
Index on (CompletedAt) INCLUDE (Amount)Index Seek164205 ms

The obvious change did nothing. The query also reads Amount, so a seek on a narrow index needs a lookup per row and the optimizer kept the scan. Only a covering index moved it: 6,700 reads to 164, a 40× reduction, with the plan switching from scan to seek. Adding an index and adding the right index are different operations.

Scope: one synthetic table, warm cache, single session, aggregate over one month (27,000 of 1,000,000 rows). The lab database was dropped after the run.

Concurrency

Blocking, measured

Two sessions updated the same row. The first held the update in an open transaction; the second waited until its three-second timeout expired and was cancelled. The wait was observed, not inferred from documentation, and the transaction was rolled back afterwards.
