Investigation P-03 · Change and recovery

Change, failure and recovery: an unbounded update and a point-in-time restore

A mass update that drifts balances, a guarded migration, blocking measured with and without RCSI, and a point-in-time restore compared row for row.

1. Documented problems

  • Clerk, 6 February 2025. A manually executed UPDATE to deprecate a feature for 3,700 customers set false values to "true" in a jsonb field. Downtime for those customers began at 09:43; the bulk corrective update finished at 10:06 — 26 minutes. Two amplifiers: the write bypassed runtime type enforcement, and an aggressively configured retry increased blast radius. Remediation included restricting direct database access and mandatory staged rollouts.
  • ECB TARGET Services, 27 February 2025. T2 and T2S were unavailable for roughly 10 and 8 hours. The initial hypothesis was a DB2 malfunction, which delayed failover because software faults replicate to the secondary site. The actual cause was two redundant Ethernet ports failing simultaneously on a storage control unit, saturating DB2 buffer pools. The contractual 60-minute RTO was missed because integrity checks on the secondary site took longer.

Both are documented incidents. The storage failure here is modelled at the database layer, not reproduced in hardware.

2. Technical problem

A single unbounded UPDATE can rewrite an entire table in one statement; an unsafe migration can be attempted on a populated table; a long transaction can block readers; and recovery must restore the pre-change state exactly, with the database restore time kept separate from service recovery.

3. Laboratory design

AFS_Lab_Change is created from scratch, placed in FULL recovery, seeded with 10,000 accounts (total 12,495,000.00, checksum 2,560,002), backed up, then exposed to four scenarios. It is dropped at the end so it never enters the portfolio inventory.

6. What the restore proves — and what it does not

It proves that the backup chain is complete and that the database can be returned to a chosen second before a bad change, with the exact pre-change checksum. It does not prove that the application recovers in the same time, that the storage fault would be diagnosed correctly, or that the RTO target is met end to end.

7. Limitations

  • Single instance; no Always On, no secondary site, no hardware fault injection.
  • 10,000 rows; the restore timing does not transfer to a large database.
  • READ_COMMITTED_SNAPSHOT changes concurrency semantics; it was applied to a disposable database only.
  • The failure detection uses expected invariants supplied by the operator — in production these must come from a trusted baseline.

8. Production considerations

Change review must require a predicate and an expected row count; migrations should be validated against a production-shaped copy; direct ad-hoc updates should be restricted to emergencies and logged; restore drills should record both database and service recovery; and RTO claims should name what is being timed.

11. What this does not prove

That the same recovery time holds at production size, that a storage-hardware fault would be diagnosed as the ECB event was, or that application-level recovery meets the same target. It proves the database-level control and the measurement discipline, and it keeps the two timings apart.
