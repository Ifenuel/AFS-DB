Investigation P-01 · Payment integrity

Payment integrity: dry posting, duplicates, concurrency and ledger recovery

Credits without debits: a dry posting, duplicate requests and a concurrent spend reproduced, then closed with one transaction, idempotency and a guarded update.

It is not a reproduction of any company's system or incident.

1. Industry context

Nigerian instant payments settle across a national switch and dozens of institutions. A payment is accepted by one bank, credited by another, and reconciled later. When the debit and the credit are not committed together, the ledger can create money — and the error is often found in settlement review, days after customers have withdrawn it.

2. Documented problem

  • NIBSS, 6–9 September 2024. A fault in the NIP engine credited beneficiary accounts without executing the corresponding debits — "dry posting". ₦13.66bn across 176 beneficiary accounts in 19 institutions. NIBSS detected it during routine settlement review on 9 September, not from the transaction path. Banks required court orders before reversing, so recovery moved to the Federal High Court.
  • Keystone Bank, February 2025. Account balances were inflated by "technical glitches", permitting ₦5.7bn of unauthorised withdrawals across 21 accounts; a court froze accounts on 18 February 2025.

What the sources establish: the mechanism (credits without debits; balances that do not match any legitimate credit) and the consequence (legal recovery, frozen funds, delayed detection). What they do not establish: the code defect, component, release or database behaviour behind either event. No such claim is made here.

4. Technical problem statement

A payment processor that (a) commits the debit and the credit in separate transactions, (b) has no idempotency constraint, (c) writes balances from a previously read value, and (d) has no reconciliation, will produce orphaned postings, duplicate charges and balance drift under ordinary failure and retry conditions. Detection falls to a later settlement review.

5. Hypothesis

Each defect independently produces a specific, detectable break type; fixing all four eliminates those breaks under the same injections, with no silent loss of legitimate postings.

6. Laboratory architecture

client (Python/sqlcmd)
   └─ paylab.usp_Submit_Unsafe | usp_Submit_Safe
        ├─ paylab.PaymentIntent  (RequestId, IdempotencyKey, state)
        ├─ paylab.Account        (materialised Balance)
        ├─ paylab.LedgerEntry    (double-entry: D and C, signed by direction)
        ├─ paylab.PaymentEvent   (append-only lifecycle)
        ├─ paylab.Outbox / Inbox (transactional messaging, dedupe)
        ├─ paylab.ReconRun / ReconBreak (typed breaks)
        └─ paylab.ExceptionQueue (operator work)

200 synthetic accounts, opening balance 10,000 each. The schema mirrors payment.Payment and account.AccountLedgerEntry without modifying them; the portfolio tables remain the published evidence.

7. Environment

  • SQL Server 2025 Developer Edition 17.0.1000.7, single instance.
  • Python 3.14 driver orchestrating sqlcmd sessions; concurrency is two real, simultaneous client processes.
  • No new dependency, service or licence.

8. Initial state

200 accounts × 10,000 = 2,000,000.00 total; zero intents, zero ledger entries, zero breaks.

The duplicate scenario is the most instructive negative result: three identical charges produced zero reconciliation breaks, because a duplicate is internally consistent — debit equals credit on each copy. Only a cross-request check (same RequestId posted more than once) finds it. The investigation query reports it as DUPLICATE_REQUEST with IntentCount = 3; the reconciliation engine alone does not. That gap is real and is addressed by the idempotency constraint, not by reconciliation.

11. Root cause

DefectMechanismObserved consequence
Separate commitseach statement autocommits; no transaction spans debit and creditdebit survives the crash, credit never happens
No idempotencyRequestId indexed but not uniqueretry posts a second, fully balanced payment
Read-modify-writeUPDATE ... SET Balance = @balance - @amount from a stale readboth sessions pass the balance check; 16,000 leaves a 10,000 account
No reconciliationnothing compares intent, ledger and balancethe drift is invisible until someone looks

12. Engineering solution

  1. Atomic posting — one transaction covers intent, debit, credit, events and outbox.
  2. Idempotency — filtered unique index on IdempotencyKey; replay returns the original payment.
  3. Guarded update — SET Balance = Balance - @amount WHERE AccountId = @id AND Balance >= @amount; the predicate is evaluated under lock, so concurrent attempts cannot both pass.
  4. Invariant — inside the transaction: exactly two entries and SUM(D) - SUM(C) = 0, else THROW and roll back.
  5. Terminal states — FAILED with a failure code is recorded, not swallowed; failures go to an exception queue.
  6. Outbox — the event row is committed with the payment, so a crash before publishing loses nothing.
  7. Inbox — redelivered messages are recorded once.

31 assertions, all executed and passing (evidence/research/P-01/RESULTS.md). They cover: dry-posting detection, duplicate counts and balances, drift detection, replay behaviour, rollback completeness, concurrency outcome, reconciliation cleanliness, outbox publishing, inbox dedupe and payment traceability. 16. Limitations

  • Single instance; no network, no MSDTC, no real switch or card network.
  • Synthetic accounts and amounts; 200 accounts is not a volume test.
  • The 400 ms think-time is injected to widen the race; a real system can lose the update at any timing.
  • Reconciliation runs on demand, not continuously.
  • Oracle/MySQL were not part of this case.
  • Nothing here proves how NIBSS or any bank implemented its posting path.

17. Residual risks

Idempotency-key retention and reuse across retries; outbox publishing is at-least-once, so consumers must dedupe; reconciliation is a batch control, not a prevention control; a compromised application login can still post balanced but fraudulent entries — which is the subject of P-04.

18. Production considerations

Keys should be client-supplied, bounded in lifetime and stored with the payment; reconciliation should run per institution and per settlement window with explicit tolerances; ledger rows should be append-only with no update grant; breaks need an owner and an SLA; and detection latency should be alarmed, because the NIBSS case was found in settlement review rather than in the payment path.

21. What this does not prove

It does not prove that the fix works across services or hosts, that it scales, or that it matches any real payment processor's design. It proves that in this laboratory, under these injections, the four defects produce specific breaks and the four controls eliminate them, with every assertion executed.
