Restore drill

Migration as the proof

Nine databases were copied with COPY_ONLY backups, verified, then restored with WITH MOVE into the Developer instance. The post-restore inventory matched 74 of 74 lines, and DBCC CHECKDB reported zero allocation and zero consistency errors.

Measured

What the log history shows

At the 16:20 instance-time capture on 25 November, every FULL database had a log backup under two minutes old. That is an observation, not an RPO. The msdb history also holds a real gap from 17:35 to 20:54 on 24 November, when no log backup ran; the configured schedule is not the same thing as a guaranteed recovery point. Full database backups are recorded with msdb type D and verified against the backup header (RESTORE HEADERONLY reports BackupType = 1).

Timed drill

How long a real recovery takes here

Not an estimate. AFS_CoreBanking was restored from the last full backup plus all 19 log backups to the end of the chain, into a throw-away database, then integrity-checked and dropped. Three runs, same host, same media.

Scope of the measurement. A 28 MB database restored from local disk on the same host, without a file transfer or an application cutover. That isolates database recovery: the part a DBA controls. A service-level RTO also carries storage throughput, a restore host and application sign-off, which is why the target for this project stays at 60 minutes and the 7.5 s figure is reported as a floor, not a promise.

Re-verified 2026-11-25

Read back, restored to a timestamp, and watched

The earlier pass proved the schedule and timed one restore. This one proved the media, proved STOPAT on the Developer instance, and put the checks on a schedule.

Every backup read back

RESTORE VERIFYONLY WITH CHECKSUM against the newest full backup of all nine databases: all verified, 0.7–14.4 MB each, 39–144 ms per file. msdb proves a backup was written; this proves it can still be read.

STOPAT, re-run on Developer

A marker row was inserted, logged, deleted, then recovered by restoring full plus logs to one second before the delete. Exactly one row came back, in 0.75 s, on a throwaway database that was dropped afterwards.

Backups on a schedule

Oracle runs a daily 02:00 RMAN job and MySQL a 02:30 dump, both battery-safe and catching up after a missed start. First runs returned 0.

A check that can fail

An hourly monitor reads the age of each FULL database's log backup, Oracle FRA usage, the last RMAN run and the newest MySQL dump. Its thresholds were deliberately tightened to confirm it reports CRITICAL and exits non-zero instead of always saying OK.
