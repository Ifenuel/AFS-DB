Investigation P-04 · Privileged access and audit

Privileged access and audit evidence

An application holding CONTROL and erasing its own trail, then least privilege, denied direct writes and an audit trigger that names the caller.

Status: PASS — 11/11 assertions executed · Date: 2026-11-25 Environment: AFS_Payments, schema paylab; principals paylab_app and paylab_auditor (no logins) Classification: controlled laboratory demonstration of over-privilege and missing audit evidence. No external system or real account is used.

1. Documented problem

  • Clerk, 6 February 2025. The outage began with a database query executed directly against production, outside the change-management path and without runtime type enforcement. One remediation was to restrict direct database access to genuine emergencies.
  • Seplat Energy 2024 Integrated Annual Report. Cyber security is ranked the number-one risk; the information security risk explicitly covers IT/OT breaches and IT continuity disruption; control of access rights and ISO 27001 external review are stated mitigations. The company reports no material IT breach in 2024.
  • AFS INC-007 already records an unauthorised-access drill in this estate.

I make no claim that any named company ran the configuration reproduced here.

2. Technical problem

When an application principal owns the schema, it can rewrite or delete ledger rows. If no in-database audit exists, the change leaves no evidence, and the only record is whatever the application chose to log. Least privilege without audit gives denial but no attribution; audit without least privilege gives attribution after the damage.

3. Baseline (deliberately unhardened)

ControlState
paylab_app permissionCONTROL on schema paylab (1 grant)
Ledger UPDATEallowed
Ledger DELETEallowed
Audit triggerabsent
Audit rows for those changes0

Executed with EXECUTE AS USER = 'paylab_app': one UPDATE and one DELETE both succeeded, and the security log stayed empty.

4. Fix

  • REVOKE CONTROL ON SCHEMA::paylab FROM paylab_app.
  • Grant EXECUTE on paylab.usp_Submit_Safe and usp_TracePayment; SELECT on the payment tables.
  • DENY UPDATE, DELETE on paylab.LedgerEntry; DENY UPDATE, DELETE, INSERT on paylab.SecurityLog; DENY ALTER on the schema.
  • paylab_auditor: SELECT on the schema, DENY INSERT, UPDATE, DELETE.
  • AFTER INSERT, UPDATE, DELETE trigger on paylab.LedgerEntry writing the calling principal, action, object and row count to paylab.SecurityLog.

The application still works because it calls the procedure; direct table access is removed. The DENY is explicit so a future role grant cannot silently restore write access.

6. Why ownership chaining matters

The procedure and its tables share an owner, so the procedure can write to tables the caller cannot touch directly. That is the intended boundary: the API is the only write path, and the trigger records who used it. It also means the DENY is not a substitute for reviewing what the procedure itself does.

7. Failed-login detection

Using the existing AFS_Audit.security.SecurityEvent data, a simple query counts failures per principal. In this estate 20 failed events are present, concentrated on AFS_App. A production version would add a time window, a threshold and a baseline, because a count without a rate is not an alert.

8. Where I bounded the test

  • The audit trail is an in-database trigger, not SQL Server Audit and not a SIEM feed.
  • An attacker with ALTER or CONTROL could disable it — precisely why DENY ALTER is part of the fix.
  • Denied statements never execute, so the engine error (Msg 229) evidences them, not the trigger. Capturing attempts centrally would need server audit or extended events.
  • The principals have no logins, so I test no authentication or password policy.
  • Detection is a query, not a scheduled alert.
  • I make no claim about any bank's access model.

9. Production considerations

Separate the application role from the deployment role; never grant schema CONTROL to an application; keep audit outside the reach of the audited principal; ship audit rows to an append-only store; alert on privilege changes and on failed-login rate; and review grants periodically against a baseline, because permission drift is gradual.

10. Runbook

# baseline -> hardening -> denial -> attributed API write
python tools/security/run_security.py

# inspect the audit trail
sqlcmd -E -C -S . -d AFS_Payments -Q "SELECT TOP 20 * FROM paylab.SecurityLog ORDER BY AuditId DESC;"

# access review
sqlcmd -E -C -S . -d AFS_Payments -Q "SELECT p.name, dp.permission_name, dp.state_desc FROM sys.database_permissions dp JOIN sys.database_principals p ON p.principal_id=dp.grantee_principal_id WHERE p.name LIKE 'paylab%';"

12. What I am not claiming

I am not claiming the audit trail is tamper-proof against a determined administrator, that it replaces a SIEM, or that the permission model matches any real bank. I am claiming that over-privilege is demonstrable, that removing it blocks the write while the API still works, and that legitimate writes become attributable.
